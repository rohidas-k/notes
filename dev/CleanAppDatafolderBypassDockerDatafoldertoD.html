Clean AppData folder & Bypass Docker Data folder to D:

A 14 GB jump in a single day inside your C:\Users folder is a massive spike, but it is a very common side effect of intensive local development setup and system migrations.

Since we just ran deep Docker rebuilds, WSL distributions exports, and package cleanups, Windows likely dumped massive amounts of temporary staging files, extraction caches, and environment logs into your hidden user profile directories.

Instead of hunting folders blindly, let's find the exact culprit in 60 seconds using a quick diagnostic script, followed by the specific steps to wipe it out.

Step 1: Find the Exact Bloated Folder

99% of hidden developer bloat hides inside a invisible folder called AppData inside your user directory. Let's run a safe PowerShell script to scan your user folder and list exactly which sub-folders are holding the most gigabytes.

Open your regular Windows PowerShell window and paste this script:

PowerShell

# Navigate to your personal user profile folder

cd $env:USERPROFILE

# Scan and list the sizes of top-level folders (this may take a minute to calculate)

Get-ChildItem -Force | Where-Object { $_.PSIsContainer } | ForEach-Object {

    $size = (Get-ChildItem $_.FullName -Recurse -File -ErrorAction SilentlyContinue |

             Measure-Object -Property Length -Sum).Sum

    if ($size) {

        [PSCustomObject]@{

            Folder = $_.Name

            SizeGB = [Math]::Round($size / 1GB, 2)

        }

    }

} | Sort-Object SizeGB -Descending

What to look for in the output:

  • If AppData is the highest number (e.g., 20+ GB), the space is trapped in temporary program files or development tool caches.
  • If Saved Games or .vhdx files appear elsewhere, a virtual image or workspace cache took up residence there.

Step 2: Clear the 3 Most Likely AppData Hogs

Based on your recent development pipeline activity, these three hidden areas are the prime suspects for that sudden 14 GB spike:

Culprit A: The WSL/Docker Staging Remnants (AppData\Local\Temp)

When you ran wsl --export docker-desktop, Windows had to compress and stage a multi-gigabyte package. It uses your user account's local Temp directory to unpack and organize these layers. If the terminal session closed or refreshed, those massive temporary compressed files frequently stay behind.

  • How to wipe it: Press Windows Key + R, type shell:localappdata and press Enter. Open the Temp folder. Select everything inside (Ctrl + A) and hit Delete. Skip any single file that says it's currently open in another program.

Culprit B: Browser & DevTools State Caches

Repeatedly running app wizards, local server instances, and testing loops causes browsers (like Google Chrome or Edge) to write heavy logs, IndexedDB databases, and site tracking histories inside your user profile.

  • Where it lives: AppData\Local\Google\Chrome\User Data\Default\Cache
  • How to wipe it: Open your web browser, press Ctrl + Shift + Delete, change the time range to "All Time," check Cached images and files, and click clear.

Culprit C: IDE & Extension App Data (AppData\Roaming\Code)

Code editors like VS Code maintain massive index trees, file histories, and extension caches for every workspace folder you open or modify.

  • How to check/wipe it: Inside AppData\Roaming, look at the Code folder. If you want a fresh start on your editor history without losing your installed extensions, you can safely wipe out the AppData\Roaming\Code\Cache and AppData\Roaming\Code\CachedData sub-folders.

It scans your entire drive in less than 3 seconds and highlights the exact large files inside C:\Users as colored blocks so you can right-click and delete them instantly.

Step 1: Run the AppData Drill-Down Script

Paste this quick script into your PowerShell window. It will look inside your Local and Roaming developer folders and print out any folder taking up more than 1 GB of space:

PowerShell

# Drill down into AppData subfolders to find the exact source of bloat

"Local", "Roaming" | ForEach-Object {

    $parent = $_

    Get-ChildItem "$env:USERPROFILE\AppData\$parent" | Where-Object { $_.PSIsContainer } | ForEach-Object {

        $size = (Get-ChildItem $_.FullName -Recurse -File -ErrorAction SilentlyContinue | Measure-Object -Property Length -Sum).Sum

        if ($size -gt 1GB) {

            [PSCustomObject]@{

                Location = "AppData\$parent"

                Folder   = $_.Name

                SizeGB   = [Math]::Round($size / 1GB, 2)

            }

        }

    }

} | Sort-Object SizeGB -Descending

Step 2: The Immediate Nuclear Cleanups

While that script processes, you can safely run these two commands to wipe out the folders most likely responsible for the 14 GB jump:

If you use tools like npx, yarn, or build utilities, they store temporary versions in your local profile directory. Flush them with this line:

Why is Docker still taking up 18 GB on C:?

When we ran the migration to move Docker to your D: drive, the wsl --unregister command successfully deleted the active distribution. However, because your system didn't recognize the name docker-desktop-data earlier, its physical virtual disk file (ext4.vhdx) was left abandoned as an orphaned "ghost file" inside your C: drive AppData folder.

Since your live Docker application is now running out of D:\DockerData, this 17.96 GB file on your C: drive is completely useless junk. Let's delete it right now along with the other app caches to instantly free up over 22+ GB of space.

Step 1: Liquidate the Docker Ghost File (Save 17.96 GB)

First, let's verify where that massive file is hiding on your C: drive and delete it.

  1. Completely close Docker Desktop (Right-click the whale icon in the system tray $\rightarrow$ Quit Docker Desktop).
  2. Open your regular Windows PowerShell window and run this command to find any large files lingering in that folder:
  3. PowerShell

  3. You will see the path to a giant ext4.vhdx file. Run this command to delete the orphaned folder structure on C: safely:
  4. PowerShell

Remove-Item -Path "$env:USERPROFILE\AppData\Local\Docker\wsl" -Recurse -Force -ErrorAction SilentlyContinue

Yes! We can completely bypass the C: drive and force Docker to store that massive docker_data.vhdx file on your D: drive.

In newer versions of Docker Desktop, Docker changed its architecture to store data directly in AppData\Local\Docker\wsl\disk\docker_data.vhdx instead of using standard WSL distribution points.

Here are the two best ways to force this bypass. Method 1 is the cleanest native way, and Method 2 is a hard system-level trick that guarantees it never touches your C: drive again.

Method 1: The Native Docker GUI Way (Easiest)

Docker Desktop has a built-in setting designed specifically to safely migrate this file to another drive.

  1. Open the Docker Desktop application.
  2. Click the Gear Icon (Settings) in the top right corner.
  3. In the left sidebar, click on Resources, then select Virtual disk.
  4. Look for the Disk location section. You will see it currently pointing to your C:\Users\rohid\AppData... path.
  5. Click Browse, navigate to your spacious D:\DockerData folder, and select it.
  6. Click the blue Apply & restart button at the bottom right.

Docker will automatically handle the heavy lifting, safely transfer that 17.83 GB file over to your D: drive, and delete the old file off your C: drive.

Method 2: The Hard Bypass (Directory Junction)

If your Docker GUI doesn't show that option, or if you want to create a permanent system-level rule that fools Docker into writing to your D: drive, we can create a Directory Junction.

This acts like a portal: Docker thinks it is writing to C:, but Windows secretly redirects the files instantly to D:.

Execute these commands in your Administrator PowerShell:

1. Shut down Docker and WSL

Right-click the Docker whale icon in your taskbar tray $\rightarrow$ Quit Docker Desktop, then kill the backend:

PowerShell

wsl --shutdown

2. Move the Data Folder to D:

We will move the entire wsl directory (containing your 17.83 GB disk) to your D:\DockerData folder:

PowerShell

# Create a dedicated target subfolder if it doesn't exist

New-Item -ItemType Directory -Path "D:\DockerData\wsl" -Force

# Move the data structure from C: to D: (This might take a minute to transfer the 17.8GB)

Move-Item -Path "$env:USERPROFILE\AppData\Local\Docker\wsl\*" -Destination "D:\DockerData\wsl\" -Force

3. Establish the Hard Bypass Link

Now, we create the junction point. This leaves a virtual shortcut on your C: drive that points directly to your D: drive folder:

PowerShell

cmd /c "mklink /j `"$env:USERPROFILE\AppData\Local\Docker\wsl`" `"D:\DockerData\wsl`""

(You should see a message stating: Junction created for...)

4. Test and Verify

Open your Windows File Explorer and navigate to C:\Users\rohid\AppData\Local\Docker\. You will see a folder named wsl with a tiny shortcut arrow on it.

Start Docker Desktop. It will launch perfectly, but your C: drive will remain completely empty of any new data—every single byte will be written safely to D:\DockerData\wsl\disk\docker_data.vhdx!

  3. PowerShell

Since your active Docker data is now running out of your D: drive, the old folder on C: is completely safe to delete. Run this command to force-delete the old 17.83 GB file path:

PowerShell

Remove-Item -Path "$env:USERPROFILE\AppData\Local\Docker\wsl" -Recurse -Force -ErrorAction SilentlyContinue

Moving a giant 18 GB virtual file across drives causes Windows to create heavy volume shadow copies and system data fragments in your user temporary folder. Flush them out with this line:
